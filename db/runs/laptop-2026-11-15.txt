Why the engine says date_bin
----------------------------
server/timescale.js fn() asks: SELECT to_regproc('time_bucket') IS NOT NULL.
On Tiger Data there are 20 functions named time_bucket (one per argument type). to_regproc returns NULL when a name
matches more than one function, so the answer is false and the service picks date_bin, which is plain PostgreSQL.
The momentum numbers are right, but they were not computed by the TimescaleDB function.
A check that works on both databases: SELECT EXISTS (SELECT 1 FROM pg_proc WHERE proname = 'time_bucket').
On this database it answers true. server/ is Ricky's lane, so the file was not changed here.

Why step 6 failed
-----------------
The failing line is the trend check: GET /players/Josh Allen/trend answered source "file", the test wants "database".
The route falls back to the game files when the weekly aggregate has no rows. Asked the database right after the run:
  fp_awards rows: 1218
  player_points_per_week rows: 0
  player_points_per_game rows: 14
  team_points_per_quarter rows: 8
  all three continuous aggregates: materialized_only = true, refresh policy every 1 hour
So the continuous aggregates do not include rows that are not refreshed yet (db/README.md says they do). The weekly
aggregate stays empty until its hourly refresh, and even after a refresh the test pushes new rows and expects to see
them at once, which needs: ALTER MATERIALIZED VIEW <name> SET (timescaledb.materialized_only = false) for each
aggregate, in a migration. db/ is Ricky's lane, so nothing was altered in the database or the files here.
Everything in step 6 before that line passed (push, repeat push, soccer minute, seq order, top plays, fp_awards count).
This also explains "summary: players [], quarters []" above: the per-game aggregates had no rows for week11-football yet.
